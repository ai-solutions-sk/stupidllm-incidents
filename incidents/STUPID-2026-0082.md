An Aider user working in a large repository (roughly 1,100 files, a ~179k-token
context) with a model that has no entry in Aider's `model-settings.yml`
(`qwen3.8-max-preview`, reached via an OpenAI-compatible endpoint) hit a
silent data-loss bug in the tool's edit-format handling. With no explicit
`--edit-format` flag set, Aider auto-selected the `whole` format for the
unlisted model. The model, however, responded with a standard unified diff
containing correct, well-reasoned changes — not a `whole`-format rewrite.
Aider's parser could not match the response against the format it expected,
concluded there were "no tracked changes," and discarded the entire response
without any warning or error message. The user was left with an empty,
no-op-looking turn and no indication that the model had actually done real
work that Aider had then thrown away. The reporter confirmed the fix:
explicitly passing `--edit-format diff` avoided the bug entirely, isolating
the cause to the auto-selected format guess rather than the model's output.
No maintainer response had landed as of this write-up. It is the third
distinct silent-success code path reported in Aider within roughly the same
period, alongside separate issues in unified-diff partial-application
warnings (#5573) and headless-mode exit-code handling (#5552) — different
functions, same shape: the tool's own logic swallows a failure or discards
real work, and nothing tells the user or caller it happened.
