## What happened

A user asked Claude Code to fast-forward a dirty feature branch — one with
uncommitted changes to `README.md`, `DESIGN.md`, and a file named
`lets-code` — onto a `main` branch that had been rewritten, while keeping
the uncommitted work intact. The session ran on Claude Code 2.1.295 with
`claude-fable-5-1`, on Linux aarch64 (a Raspberry Pi), in auto permission
mode.

To carry the uncommitted changes across the fast-forward, the agent ran:

```
git stash push
git merge --ff-only main
git checkout stash@{0} -- README.md
git reset -q
git stash drop
```

It restored only `README.md` from the stash — the one file it needed for
the merge — then dropped the stash, discarding `DESIGN.md` and
`lets-code` along with it. The agent noticed the missing changes from `git
status`, found the dangling stash commit with `git fsck --unreachable`, and
recovered the files. About 15 minutes later in the same session, it ran the
exact same five-command sequence again, and dropped the same uncommitted
work a second time, requiring the identical recovery.

## Why it matters

Auto mode's command-safety classifier did not flag `git stash drop` as
destructive, because no single command in the sequence is obviously unsafe
on its own — the danger is in the combination: checking out one of several
stashed paths and then dropping the stash as if the restore were complete.
Both losses were recoverable only because the stash's underlying commit
object had not yet been garbage-collected; `git stash drop` removes the
stash *reference*, not the commit it points to, so `git fsck --unreachable`
could still find it. That window closes once git's garbage collector runs,
at which point the same sequence would have caused permanent loss.

The second occurrence, repeating the identical mistake minutes after
recovering from the first, is the more notable finding: the agent diagnosed
and fixed the exact failure once, then executed the same unsafe sequence
again without adapting.
