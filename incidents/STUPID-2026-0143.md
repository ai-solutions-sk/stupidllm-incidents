A Cline user (feiiiiii5) filed an issue on October 1, 2026 describing a gap
in Cline's agentic context compaction: when a long session triggers
automatic summarization of prior history, the code path that decides
whether to install the resulting summary only checks for a completely
empty result. It does not check `SummaryGenerationResult.incompleteReason`,
the field that is set when generation was cut off partway through. A
summary that is truncated but non-empty is installed exactly as if it were
complete, with nothing in the application logs distinguishing the two
cases.

The reporter traced this to have become more likely after PR #13137, which
began applying the user's own max-output-tokens setting to the
summarization request itself — so a user who had lowered that setting for
unrelated reasons can now unknowingly cause their own compaction summaries
to be truncated. A second commenter, chenhz01, confirmed the problem the
same day and proposed warning the user and retrying with a smaller input
before falling back to installing a flagged-incomplete summary. A third
commenter, aldi949, flagged the downstream consequence on October 9:
because the agent has no way to know its own context is incomplete,
"mandatory requirements can disappear" from the task state after
compaction without any signal that this happened.

The reporter opened three follow-up items in response — PR #14741 (making
truncation observable in logs and adding one retry), issue #15005
(proposing a fidelity signal for whether retained context is provably
complete), and discussion #15006 (requesting a user-visible marker on
truncated summaries) — but said explicitly that the retry PR "does not
claim" to preserve requirements that a truncated summary already dropped.
As of this writing the original issue remains open with no maintainer
decision on which fix to adopt, and the risk aldi949 described — a
requirement silently vanishing from a task's working context mid-session —
is unresolved.
