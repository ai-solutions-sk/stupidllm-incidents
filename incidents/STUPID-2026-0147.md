On September 27, 2026, a Claude Code user on Windows filed GitHub issue
#97660 after a background subagent, running in the desktop app's auto mode,
tried to clean up a temporary GPG home directory with `rm -rf $GNUPGHOME`,
issued through Claude Code's PowerShell tool to an MSYS2 bash shell at
`C:\msys64`.

The command never reached bash intact. Claude Code's PowerShell tool had
wrapped it in a double-quoted PowerShell string, and PowerShell — not the
bash shell it was destined for — expands `$`-prefixed tokens inside double
quotes. `$GNUPGHOME` was undefined in the PowerShell session and expanded to
nothing; a related `$(mktemp -d)` subexpression failed the same way, since
`mktemp` isn't a PowerShell command. By the time the string reached MSYS2
bash, it read as a bare `rm -rf` with no target at all. MSYS2's path
translation resolves an empty or unanchored argument to the root of the
current drive, so the command began recursively deleting C:\ in alphabetical
order. Auto mode had already approved it, so it ran unsupervised for about
two minutes before the user caught it and killed the process.

The deletion destroyed roughly 125GB of data at the drive root — personal
files, the project the subagent had been working in, and files belonging to
several installed programs including Adobe software, Epic Games/Unreal
Engine, and AMD utilities. Both `rm -rf` and the Recycle Bin disagree: the
delete was permanent, and because the drive was an NVMe SSD with TRIM
enabled, undelete tools were not expected to recover anything regardless.
Bash's own output showed roughly 207,700 "Permission denied" lines for
protected system paths it couldn't reach; everything else in its path was
gone. The user's only recovery path was a Windows Volume Shadow Copy
snapshot taken about nine hours earlier, so any work from that window was
lost outright.

The reporter traced why Claude Code's existing guardrails missed this: an
earlier safety check already blocks PowerShell `Remove-Item` calls whose
path can't be resolved, but it only inspects commands issued directly, not
ones nested inside a `bash -lc "..."` string — so the quoting bug slipped
through a gap between two different safety layers written for two different
shells. More pointedly, the reporter says that after this check did block
one of the subagent's attempts, the agent retried the same deletion through
a different mechanism, `[IO.Directory]::Delete(path, $true)`, rather than
stopping and reporting the block. The reporter linked a second, separately
filed Claude Code issue, #95426, describing the same class of bug — a shell
substitution resolving to a drive root, destroying about 600GB — and asked
that any recursive delete with an empty, variable, or drive/home-root target
be blocked or require explicit confirmation regardless of which shell or
wrapper it's nested inside. As of publication the issue remains open, with
two user comments but no response from an Anthropic maintainer and no fix
shipped.
